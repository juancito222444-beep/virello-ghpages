Construye “STUDIO DE ANTO”, una aplicación real de agentes de IA colaborativos con una oficina virtual isométrica, utilizando como antecedentes el archivo studio_de_anto.py y el video adjunto.

Quiero una aplicación funcional, visualmente cuidada y ejecutable sin APIs de pago. No quiero otro notebook de Colab, formularios de ipywidgets, chats con respuestas fijas ni personajes representados únicamente por emojis.

Tu tarea es desarrollar el proyecto, verificarlo y entregarlo preparado para funcionar. No te limites a explicar cómo podría hacerse.

# 1. Qué quiero conseguir

Una oficina virtual donde pueda ver personajes trabajando, seleccionar un agente, conversar con él, subir archivos de datos y pedir un análisis.

Los agentes deben colaborar mediante tareas y resultados compartidos. Quiero ver quién está trabajando, qué está haciendo, qué entregó y qué falta revisar.

Ejemplo:

Subo un Excel y escribo:

“Compara los ingresos por producto y región, identifica datos faltantes y prepara gráficos e informe”.

El coordinador debe interpretar la solicitud, proponer un plan adecuado al archivo y distribuir el trabajo entre analista, revisor, visualizador y redactor.

El resultado debe incluir tablas correctas, gráficos, explicación, limitaciones y archivos descargables.

La aplicación también debe permitir conversar y organizar proyectos sin exigir subir un archivo.

# 2. Audita el archivo adjunto antes de reutilizarlo

El archivo original tiene problemas concretos:

- Inserta mensajes del usuario directamente en HTML.
- El manifiesto puede anunciar archivos que no se generaron.
- Las ejecuciones reutilizan identificadores y nombres de archivos.
- Imprime una ruta como si fuera una descarga.
- No conecta Ollama ni otros modelos.
- No implementa una colaboración real entre modelos.

Verifica estos puntos contra el archivo.

Conserva el original como referencia. Reutiliza únicamente lógica útil que puedas corregir y probar. No construyas la aplicación nueva alrededor de las limitaciones del notebook.

- No presupongas que read_excel siempre devuelve un DataFrame.

Para CSV:

- Muestra vista previa.

Conserva el archivo original y registra las transformaciones.

Herramientas permitidas:

- Inspección de esquema.
- Conteos y valores faltantes.
- Duplicados.
- Filtros.
- Ordenamiento.
- Agrupaciones.
- Suma, media, mediana, mínimo, máximo y conteo.
- Columnas derivadas mediante operaciones validadas.
- Series temporales cuando haya fechas válidas.
- Gráficos.
- Exportación.

El modelo decide qué operación proponer. Los valores numéricos los calcula Python.

No uses exec ni eval sobre código generado por el modelo. Implementa operaciones con argumentos validados.

No sumes identificadores ni promedies códigos porque sean numéricos.

No elimines duplicados o imputes faltantes silenciosamente.

Si “ingresos” debe calcularse como cantidad × precio, identifica las columnas, registra la fórmula y comprueba que esa definición corresponda al dataset. Si existe ambigüedad material, pregunta.

Trata NaN, infinito, fechas inválidas, archivos vacíos, encabezados repetidos y tipos mixtos.

# 11. Revisión verificable

BRUNO no debe aprobar por defecto.

Implementa comprobaciones como:

- Columnas utilizadas frente a las solicitadas.
- Filtros y periodo.
- Conteos antes y después de transformaciones.
- Total general frente a suma de subtotales cuando sea aplicable.
- Valores faltantes excluidos.
- Coherencia entre tabla y gráfico.
- Coherencia entre cifras del informe y resultados calculados.

Distingue:

- Verificación automática superada.
- Revisión por modelo.
- No verificable.
- Requiere decisión del usuario.

Una segunda opinión de un modelo no reemplaza una comprobación matemática.

Si introduces una discrepancia de prueba, el revisor debe detectarla y bloquear la aprobación correspondiente.
